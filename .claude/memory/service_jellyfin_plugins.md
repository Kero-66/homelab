### Virtual library setup (done for kero66, 2026-07-03)
- JellyNext writes stub content to `/config/data/plugins/Jellyfin.Plugin.JellyNext/jellynext-virtual/{userId}/{movies_recommendations,shows_recommendations,shows_nextseasons}` (container path — note: **not** `/config/plugins/...` as one older doc revision of JellyNext's README states; verify actual path via `docker exec jellyfin find /config/data/plugins/Jellyfin.Plugin.JellyNext -maxdepth 3` if paths seem wrong after a version bump).
- JellyNext does NOT auto-create Jellyfin libraries — after the "Sync Trakt Content" scheduled task runs once per user (creates the stub files), you must manually create 3 libraries per user pointing at those 3 folders (`collectionType=movies` for recommendations, `collectionType=tvshows` for the other two). Used `POST /Library/VirtualFolders?...&refreshLibrary=true` — remember the earlier JellyBridge gotcha: `refreshLibrary=false` leaves the library empty/invisible until a manual `/Library/Refresh`.
- **Gotcha hit while scripting this**: in a bash loop, do NOT name a loop variable `PATH` — it silently clobbers the shell's real `$PATH` and breaks every subsequent command (`python3: command not found` etc.) with no obvious error pointing at the cause. Use a different variable name (e.g. `LIBPATH`).
- **Official Trakt plugin exclusion (done)**: added the 3 JellyNext stub folder paths to the official `Trakt` plugin's per-user `LocationsExcluded` array (`POST /Plugins/4fe3201ed6ae4f2e8917e12bda571281/Configuration`) so playing placeholder stubs doesn't get scrobbled back to the user's real Trakt watch history. `LocationsExcluded` takes filesystem paths, not library names.
- **Repeat per additional user**: get their Jellyfin user GUID, trigger/wait for their Trakt authorization + first sync, create their 3 libraries, add their 3 stub paths to the Trakt plugin's exclusion list for their `TraktUser` entry.
- **Gotcha found 2026-07-09 — leaks into "Recently Added"**: JellyNext's virtual libraries' stub files showed up mixed into the home screen's "Recently Added Movies"/"Recently Added Shows" rows.
  - **First fix attempted (WRONG, didn't work)**: native Jellyfin `Configuration.LatestItemsExcludes` per-user setting. Did not stop the leak — this server uses the **Home Screen Sections** plugin (IAmParadox27, guid `b8298e01-2697-407a-b44d-aa8dc795e850`, installed via the same `File Transformation`/IAmParadox repo as other plugins), which generates its own "Recently Added" rows via custom code that ignores `LatestItemsExcludes` entirely — it aggregates **every library whose `CollectionType` matches** (movies/tvshows) unless told otherwise (source: `RecentlyAddedSectionBase.cs`, filters `GetVirtualFolders()` by `CollectionType`, no exclude-list concept).
  - **Actual fix**: Home Screen Sections plugin's own config has `DefaultMoviesLibraryId` / `DefaultTVShowsLibraryId` fields (empty by default = aggregate all matching-type libraries). Set both to the real Movies/TV Shows library IDs via `POST /Plugins/b8298e01-2697-407a-b44d-aa8dc795e850/Configuration` — this is a **global plugin setting, not per-user**, so it only needs doing once regardless of how many users get JellyNext libraries later.
  - **Lesson**: when a Jellyfin behavior doesn't match native Jellyfin's documented settings, check which plugin might be overriding/replacing that home screen feature before assuming the native fix should have worked — this server has `Home Screen Sections` + `Plugin Pages` + `Media Bar` installed, several of which customize home screen behavior beyond stock Jellyfin.
  - **Second attempted fix (partial, insufficient)**: Home Screen Sections plugin's own `DefaultMoviesLibraryId`/`DefaultTVShowsLibraryId` config fields. Read source (`RecentlyAddedMoviesSection.cs`, `CreateInstances()`) — these fields **only control the section's click-through/"see all" link target**, not the actual item list. Also hit a format bug: saved the ID in Jellyfin's dashless API format (`f137a2dd21bb...`) but .NET's `Guid.ToString()` (used for the match) produces dashed format (`f137a2dd-21bb-...`) — the match silently failed, causing fallback to the *alphabetically first* matching-type folder ("kero66's Movie Recommendations" sorts before "Movies"), which is why clicking the row took the user there. Fixed by converting to dashed GUID format.
  - **Root cause, unfixable via config**: read `RecentlyAddedSectionBase.GetResults()` and `LatestSectionBase.GetResults()` directly — **every** content-list method in this plugin (`RecentlyAddedMovies/Shows`, `LatestMovies/Shows`) filters libraries purely by `CollectionType` match (`GetVirtualFolders().Where(x => x.CollectionType == CollectionTypeOptions)`), with **zero exclusion mechanism** anywhere in the codebase. `DefaultMoviesLibraryId` is never referenced in `GetResults()`, only in `CreateInstances()` (the link). There is no way to exclude a specific library from these rows' actual content via plugin config — confirmed by reading source, not assumption.
  - **Third attempted fix (WRONG mental model, no effect)**: disabled the 4 sections via `SectionSettings[].Enabled = false` globally, and set `useModularHome = "false"` in kero66's DisplayPreferences (client=emby). Neither did anything — `useModularHome` in DisplayPreferences.CustomPrefs is a leftover/unused key, NOT what gates modular vs classic home; the real gate is `/HomeScreen/Meta`'s `PluginConfiguration.Enabled` (global on/off for the whole plugin, would've killed ContinueWatching/NextUp/BecauseYouWatched too — too big a hammer, never actually flipped it).
  - **Actual root cause, found by reading `HomeScreenManager.GetUserSettings()`**: because these 4 sections have `AllowUserOverride: true`, each **user** has their own persisted `ModularHomeUserSettings.EnabledSections` list (JSON file on the Jellyfin server, under the plugin's config dir), populated once (e.g. on first home-screen load) and never auto-synced with later global `SectionSettings[].Enabled` changes — the sync-from-global-config code path in `GetUserSettings()` only applies to sections with `AllowUserOverride: false` (`LockedSections`). kero66 already had a personal list from before any of these fixes, containing all 4 unwanted sections, completely independent of everything I changed in the plugin's global config.
  - **Real fix (verified working via claude-in-chrome, not just API)**: `GET /ModularHomeViews/UserSettings?userId={id}` to read the user's personal list, remove the 4 section IDs from `EnabledSections`, `POST /ModularHomeViews/UserSettings` with the full modified object back. This is **per-user** — must repeat for every additional user who has customized their home screen (check their `EnabledSections` first; if they've never touched home customization, the global `SectionSettings[].Enabled = false` alone is enough, since a fresh per-user object pulls straight from global config).
  - **After ANY Home Screen Sections config or user-settings change**: always call `POST /HomeScreen/BustCache` (route is under `/HomeScreen/`, not `/Plugins/{id}/`) — this plugin caches home screen data for `CacheTimeoutSeconds` (default 86400s = 24h), so changes are invisible until busted. A server-side `curl` check of `/HomeScreen/Sections` confirming the right list, immediately followed by a **hard browser reload** (Ctrl+Shift+R) and re-checking, is the only way to be sure a fix landed — API responses being "correct" does not guarantee the rendered page matches, since there are at least 3 separate cache/override layers in play (plugin data cache, per-user EnabledSections, browser).
  - **Meta-lesson from this whole saga**: don't declare a fix done off a single successful API POST — verify end-to-end (server state AND rendered client) before telling the user it's fixed. Four rounds of "I fixed it" that weren't actually fixed (wrong field, format bug, wrong global-vs-per-user layer) burned significant trust; should have used claude-in-chrome to visually verify starting from the second attempt, not the fifth.

**Why:** user explicitly wants recs based on what they watch, using existing stack (Jellyseerr/Jellystat/Trakt) rather than adding new containers/API costs.
**How to apply:** if Jellyfin is ever rebuilt/migrated, re-add the JellyNext repo via `media/scripts/configure_jellyfin_plugins.sh`, reinstall the plugin, restore the Jellyseerr integration config above, and each user must re-do their Trakt OAuth link (tokens are stored server-side, not in this repo).

### Major version, new job-based API (found 2026-09-10, image still `:latest` — same tag, app grew underneath it)
SuggestArr has since moved to a job-based model — the old `/api/config/section/*` + single "Default Automation" job is gone, replaced by `GET/POST/PUT /api/jobs`, `POST /api/jobs/{id}/run`, `GET /api/jobs/history`, and a full request-approval workflow (`GET /api/automation/requests/workflow?status=awaiting_approval|queued|submitting|submitted|rejected|failed|blacklisted`). Four jobs exist: `Discover Movies` (id 2), `Discover TV` (id 3), `Watch History Recommendation` (id 1, `media_type: both`, the main one), `Trakt Recommendations` (id 4, disabled — see below). Auth is still `POST /api/auth/login` → `Authorization: Bearer <token>`.

**Bug found — suggestion pool dries up after a handful of approvals/rejections**: `api_service/services/tmdb/tmdb_discover.py`'s `_discover()` computes `pages_needed = ceil(max_results / CONTENT_PER_PAGE)` where `CONTENT_PER_PAGE = 20`, and **only ever fetches that many TMDB discover pages** — it does not compensate by fetching more pages when post-filtering (already-requested/downloaded/blacklisted) knocks candidates out. With the default `max_results: 5`, `pages_needed = 1`, so every run draws from the *same* fixed ~20-item TMDB page; as you approve/reject those, the pool of genuinely-new candidates shrinks toward zero and never refreshes. **Fix applied 2026-09-10**: doubled `max_results` to 10 on all 4 jobs via `PUT /api/jobs/{id}` (`{"max_results": 10}`) — still under the 20-per-page threshold so it doesn't yet force page 2, but gives more headroom before drying up. If it dries up again, push `max_results` past 20 to force real pagination. Not an upstream-reported issue as far as we found — verify against a newer image release before assuming it's still present.

**All 4 jobs have `delivery_mode: "manual"`**, which forces every discovered item to status `awaiting_approval` regardless of the global `REQUIRE_REQUEST_APPROVAL` config flag (see `requires_request_approval()` in `services/seer/seer_client.py` — job-level `delivery_mode` overrides the global default entirely). This is by design, not a bug — but it means suggestions pile up in `awaiting_approval` and block re-discovery of the same titles until a human approves/rejects them via the UI. If suggestions seem stuck, check the approval-required workflow queue first, not the discover logic.

**Trakt Recommendations job disabled 2026-09-10**: Trakt made API-app creation VIP-only on 2026-07-30 and deleted existing free-tier apps outright (not just blocked new creation) — confirmed via `POST /api/trakt/me/device/code` returning `401 invalid_client: "client not found"` even though the stored `TRAKT_CLIENT_ID`/`TRAKT_CLIENT_SECRET` are correctly formatted (64-char hex). No official reversal as of this writing; re-enabling requires either a Trakt VIP subscription to re-register the app, or waiting to see if Trakt walks the policy back. Disabled via `PUT /api/jobs/4 {"enabled": false}` rather than left to fail silently. **Not a hard dependency**: Trakt is wired into the main recommendation job (`Watch History Recommendation`) only as an optional *augmentor* (`MediaUserTraktAugmentor`, `services/trakt/media_user_augmentor.py`) that gracefully no-ops when disconnected (`if not link or not link["connected"]: return None`, wrapped in try/except) — core TMDB-similar-content recommendations off actual Jellyfin watch history keep working fine without it.

**Not a bug, just a naming trap**: "Star Wars: Clone Wars" (2003 Genndy Tartakovsky 2D micro-series, tmdb:3122) and "Star Wars: The Clone Wars" (2008-2020 CGI series) are genuinely different TMDB entries — a suggestion for the former isn't a duplicate of owning the latter, despite the near-identical title.

**Jellyseerr has no personalized recommendation engine of its own** (confirmed by reading its source, `fallenbagel/jellyseerr`) — its Discover page is Trending/Popular/Upcoming (pure TMDB charts) plus per-title "Recommendations/Similar" (a passthrough to TMDB's generic `/recommendations` for that one title, not tied to the viewer's account). SuggestArr is the only actually-personalized piece in this stack; don't expect Jellyseerr's own UI to get smarter on its own.

## Jellyfin 10 → 12.0.0 upgrade (2026-09-09) — plugin fallout
Jellyfin 12 renamed/restructured detail-page DOM classes and dropped legacy auth headers (`X-Emby-Token`/`X-Emby-Authorization`/`X-MediaBrowser-Token` → standard `Authorization: MediaBrowser Token="..."` scheme, see `ai/PATTERNS.md` "Auth header (Jellyfin 12+)"). Plugin/config fallout from the upgrade:
- **Hardware transcoding silently reset to `HardwareAccelerationType: "none"`** despite VAAPI devices/config in compose being untouched — reset back to `"vaapi"` via `POST /System/Configuration/encoding`.
- **File Transformation** (IAmParadox27) was "Malfunctioned" under v12 — its old Harmony/MonoMod-based file-patching approach broke. Fixed by upgrading 2.5.1.0 → 3.0.0.0, a full architecture rewrite to ASP.NET Core middleware (`IStartupFilter`) that serves transformed files on-the-fly instead of patching disk files — this also fixed the same-cause failures in **Home Screen Sections** and **Jellyfin Enhanced**'s script injection.
- **Jellyfin Enhanced** was stale at 9.6.2.0 (targeting ABI 10.11) — upgraded to 12.6.0.0 (native v12 build exists in the same repo).
- **Media Bar** (IAmParadox27) — **removed**, no v12 build exists upstream (latest release 2.4.13.0 still only targets `10.11.x` ABIs). This was the "Netflix-style" home banner. Its stale 2.4.4.0 build was still "Active" post-upgrade but non-functional, and its old CSS/backdrop-hover-card handling didn't degrade gracefully — see the Ultrachromic overlay bug below for the actual related-but-separate visual bug this caused confusion with.
- **Shokofin** — confirmed same story (checked 2026-09-10): no v12-targeted build in `ShokoAnime/Shokofin`'s manifest either (max targetAbi `10.11.0.0`). Never actually installed on this server even under v10 (only the repo URL was registered) — see the Shoko/Jellyfin-Enhanced note below for what *is* actually wired up.
- **TMDB_API_KEY added to Jellyfin Enhanced** 2026-09-10 (was empty; the key already existed in Infisical `/media` from the SuggestArr setup, just reused it).

### Cast & Crew hover-card overlay bug — STILL OPEN, root cause found, no fix applied
Reported symptom: on show/episode detail pages, a stray thumbnail (the Cast & Crew hover-preview card, `.card.backdropCard`) sits pinned in the top-left of the viewport and overlaps content as you scroll. **Root cause (confirmed via live DOM/CSS inspection, not the plugins)**: the **Ultrachromic** custom skin (`CTalvio/Ultrachromic`, applied via the **Skin Manager** plugin's `selectedSkin` config, `@import` from jsDelivr) has a `base.css` rule `.layout-desktop .detailImageContainer .card { position: fixed !important; }` (intentional — "stop covers from being scrolled on desktop"). Its `fixes.css` only adds the matching `padding-left: 28.45vw` (or `23.45vw` at more extreme ratios) to push page content clear of that pinned image **inside `@media (min-aspect-ratio: 1.98/1)` — i.e. only on ultrawide monitors**. On a normal ~16:9 window, nothing pushes the content over, so it renders underneath the pinned cover image. This didn't show up under Jellyfin 10 because the old client's detail-page class names didn't match this skin rule's selectors at all — v12's DOM restructure made a previously-dormant rule start firing.
- **A `data:` URI `@import` fix was attempted and reverted** (2026-09-10) — Skin Manager's `selectedSkin` field only extracts literal `@import url(...)` tokens via regex and silently drops any other content appended to the string (a raw CSS rule appended directly saves fine server-side but never renders client-side); re-encoding the fix as `@import url('data:text/css;base64,...')` was in progress when the user asked to stop chasing it. **Left in original state** (`selectedSkin` reverted to just the two original theme imports) — not fixed.
- **A JavaScript-Injector "watchdog" script workaround was also tried and rejected by the user** ("dumb fix") — it force-hid the stuck element on scroll/mouseleave, which also kills the legitimate hover-preview effect entirely. Removed.
- **If revisited**: either (a) get the data-URI `@import` approach working (needs verifying it actually lands in a rendered `<link>`/`<style>` tag, not just server-side config), or (b) open an issue against `CTalvio/Ultrachromic` for the missing non-ultrawide `padding-left` case, or (c) just switch away from a pinned-cover skin design.
