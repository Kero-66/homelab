### Real mistakes made and caught mid-session — worth reading if touching this again
- **User caught scope creep twice**: first when a separate `fix_stuck_queue_imports.sh` script was
  written instead of adding modes to the existing `import_downloads.sh` (its own header already
  claimed to be "the canonical way to import stuck/manual downloads" — no reason for a second tool
  sharing the same API helpers). Second when a generated plan file was written under `logs/` instead
  of its own directory — "that's not appropriate put it under it's own folder". Both fixed same-turn.
- **jq `capture()` footgun, hit twice.** First: a regex matched a download's *parent folder* name
  instead of the filename (no basename split first) and silently mapped every file in a 24-episode
  batch to episode 1 — caught before submitting anything, by testing the regex against a single
  filename in isolation before trusting it at scale. Second, subtler: `(.path | capture(regex)?) as
  $cap | if $cap != null then ... else . end` inside a `map()` — when the regex doesn't match, jq's
  `capture()` produces **zero outputs**, not `null`; that's not an error `?` can suppress, so the
  whole `map()` iteration for that element produces nothing and the element is silently dropped
  from the array. This ate a Koyomimonogatari NCED extras file out of a plan (12 files where 13
  should've stood). Fix: wrap in an array first — `([.path | capture(regex)] | first) as $cap` —
  which turns "zero or one" into a real value (`null` when empty) instead of vanishing. **General
  lesson for any future jq `capture`/`match` use in this repo: always wrap in `[...]  | first`
  before binding as a variable inside a `map()`, and always verify the output array length matches
  the input length after any transform that's supposed to be a 1:1 map** — this class of bug is
  silent (no error, no warning, valid JSON out) and only shows up as a missing item days later.
- A partially-written jq output got `mv`'d over the live plan file mid-edit (a syntax error caused
  jq to write nothing to a temp file, then `mv` clobbered the real plan with that empty file).
  Recovered by regenerating `--plan` fresh since nothing had been `--apply`'d yet. **Lesson applied
  for the rest of the session**: always redirect a jq transform to a *new* temp file and verify
  it (record count, `jq empty`, spot-check values) before copying it over the file being edited —
  never pipe a risky transform directly into the file you're editing.
- Confirmed via `stat` (inode + link count) on TrueNAS that re-importing an already-`hasFile:true`
  episode through this path is a genuine hardlink to the same data, not a duplicate copy — Sonarr
  treats it as an "upgrade" (deletes the old `episodefile` DB row, creates a new one) but the
  underlying file is unchanged. Confirmed no orphaned file was left behind either (only one file on
  disk for the affected episode, before and after).
- One "still importBlocked" apply-time warning (`.hack//G.U. Trilogy`) turned out to be a false
  alarm from checking the queue a moment too early — a follow-up query moments later showed it had
  cleared. Worth remembering if `--apply`'s post-submit check reports a false negative — don't treat
  the in-script check as absolutely final, a manual re-query is a good gut-check if in doubt.
